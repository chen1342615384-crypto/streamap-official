# 企业官网前后台开发指南

面向本项目（Streamap 风格企业官网）：前台展示 + 后台可改文案/图片/素材。

---

## 1. 目标与范围

### 要做成什么
- **前台**：企业官网（首页、产品、方案、新闻、关于等），面向访客
- **后台**：运营可登录，修改页面上的**文本、图片、视频、链接、列表卡片**等，改完前台生效（可先预览再发布）

### 先不做 / 可后做
- 复杂电商、会员体系、支付
- 完整多语言工作流（可先中英文静态切换，再接翻译流程）
- 重度安全加固（正式上线前再补，见第 8 节）

### 成功标准
- 运营不改代码也能换 Hero 文案、配图、新闻卡片
- 前台视觉与动效不因「接 CMS」明显变差
- 有预览/发布，避免误改直接上生产

---

## 2. 推荐总体架构

```
┌─────────────────┐     API / CDN      ┌──────────────────┐
│  官网前台 (访客)  │ ◄────────────────► │  内容 API / CMS   │
│  Vite + React   │                    │  Strapi/Directus │
└─────────────────┘                    │  或自建 Nest API  │
                                       └────────┬─────────┘
┌─────────────────┐                            │
│  管理后台 (运营)  │ ───────────────────────────┘
│  独立 React Admin│         读写同一套内容
└─────────────────┘
         │
         ▼
   对象存储 (图片/视频) + 数据库 (文案结构)
```

### 原则
| 原则 | 说明 |
|------|------|
| 前台与后台分离 | 官网继续用现有 Vite React；后台可同仓 monorepo 或独立仓库 |
| 内容与代码分离 | 可改内容进 CMS/API；布局、动效留在代码里 |
| 媒体进对象存储 | 不要只靠 `public/` 写死图片；后台上传到 OSS/S3，前台用 URL |
| 先定内容模型再写后台 UI | 字段稳定后再做管理界面，避免返工 |

### 技术选型建议（与现状对齐）

| 层 | 建议 | 备注 |
|----|------|------|
| 官网前台 | **继续 Vite + React + TS + Tailwind** | 已有 GSAP / Swiper / Globe，无需为后台换框架 |
| 内容方案 A（推荐起步） | **Strapi 或 Directus** | 自带后台、权限、媒体库，最快可用 |
| 内容方案 B | NestJS / Express + PostgreSQL + 自研 Admin | 定制强、工期更长 |
| 媒体 | 阿里云 OSS / 腾讯云 COS / S3 | 配 CDN、限制类型与大小 |
| 部署 | 前台静态托管或 Nginx；API 与后台单独部署 | 正式环境再加 HTTPS / CDN / WAF |

## 3. 分阶段实施（强烈建议按此顺序）

### 阶段 0：对齐需求（0.5～1 天）
- 列出页面清单与每页「可编辑块」
- 明确角色：谁改内容、谁发布、要不要审核
- 定域名、语言（仅中文 / 中英）

### 阶段 1：前台页面定型（当前重点）
- 按设计把页面做完：**首页 → 产品/方案 → 新闻/故事 → 关于/页脚**
- 内容可暂时写死在组件或本地 JSON
- **边做边标注**「可编辑字段清单」（见第 4 节模板）
- 本阶段**不建完整后台**，避免页面一改字段全废

### 阶段 2：内容模型与接口
- 把清单落成 CMS Collection / 数据库表
- 前台改为：`请求 API → 渲染组件`（保留 loading/兜底文案）
- 本地或预发环境联调

### 阶段 3：管理后台
- 登录、角色权限
- 按「页面 / 区块」编辑文本与素材
- 媒体库（上传、替换、删除）
- 草稿 / 预览 / 发布（建议至少有发布开关）

### 阶段 4：正式上线与安全
- HTTPS、域名、备份
- 表单防刷、后台 2FA、上传校验、安全响应头
- CDN / WAF（有正式流量后再加强）

## 4. 内容模型（后台字段怎么拆）

### 拆分原则
- **可运营改的**：标题、副文案、按钮文字与链接、图片、视频、新闻卡片列表、导航文案
- **留在代码里的**：布局栅格、动画参数、组件结构、品牌色与字体 token（除非运营明确要改主题）

### 建议按「页面 → 区块 → 字段」

示例（首页，可按实际组件微调）：

```
SiteSettings（全站）
  - logo
  - 默认 SEO title/description
  - 页脚链接组
  - 备案/联系信息

HomePage
  - Hero
      - headline, subcopy, ctaLabel, ctaHref
      - videoUrl / posterImage
  - Stats[]（数字 + 标签）
  - Stories[]（标题、说明、封面图、排序）
  - Software
      - 大卡片文案 + 图
      - 小卡片列表[]
  - News[]（类型标签、标题、摘要、封面、链接）

Nav
  - 菜单项（可先静态，后期再做成可配）
```

### 阶段 1 产出物：可编辑清单（每做一个区块就填）

| 页面 | 区块 | 字段名 | 类型 | 备注 |
|------|------|--------|------|------|
| 首页 | Hero | headline | 短文本 | |
| 首页 | Hero | subcopy | 长文本 | |
| 首页 | Hero | poster | 图片 | 建议尺寸 1920×1080 |
| 首页 | Stories | items[] | 图+标题列表 | 建议 3～6 张 |
| … | … | … | … | … |

## 5. 前台改造约定（接后台时少踩坑）

1. **组件只负责展示**：文案/图从 props 或 hooks（`useHomeContent()`）来，不要散落魔法字符串。
2. **资源路径统一**：继续用 `asset()` / 完整 CDN URL；后台返回的应是**可公网访问的绝对 URL**。
3. **列表要可增减**：新闻、故事卡片用数组渲染，不要写死 5 个并列 JSX。
4. **缺省与降级**：接口失败时显示上次缓存或占位，避免白屏。
5. **SEO（正式站）**：关键页标题、描述可配置；后续若要强 SEO，再评估迁 Next.js/SSR，**不是现在必须**。

伪代码：

```tsx
// 现在（阶段 1）
const headline = "Real-world ingenuity. Measurable impact.";

// 之后（阶段 2）
const { data } = useHomePage();
const headline = data?.hero.headline ?? "Real-world ingenuity. Measurable impact.";
```

## 6. 后台功能清单（MVP → 增强）

### MVP（够用即可上线运营）
- [ ] 管理员登录
- [ ] 按页面/区块编辑文本
- [ ] 上传/替换图片与视频
- [ ] 列表项增删改排序（Stories / News 等）
- [ ] 保存后前台可见（或「发布」按钮）
- [ ] 基础权限：至少区分「能登录的人」

### 增强（有余力再做）
- [ ] 草稿 / 预览链接 / 定时发布
- [ ] 操作日志与回滚
- [ ] 多语言字段
- [ ] 媒体库检索、文件夹
- [ ] 角色：编辑 vs 发布者
- [ ] 表单线索（联系我们）查看

## 7. 媒体与素材规范

| 项 | 建议 |
|----|------|
| 格式 | 图片 WebP/PNG/JPG；视频 MP4（H.264） |
| 上传限制 | 图片单张建议 ≤ 2～5MB；视频走单独策略或外链 |
| 命名 | 后台可自动生成 UUID；前台只存 URL |
| 替换 | 换图用新 URL 或同 key 覆盖 + CDN 刷新 |
| 尺寸 | 在可编辑清单里写清「建议像素」，减少拉伸糊图 |

---

## 8. 安全（完成主功能后再加，上线前要有）

### 开发期
- 密钥、Token 不进 Git
- 后台不要裸奔在公网无鉴权

### 正式上线前
- 全站 HTTPS
- 安全响应头（HSTS、CSP 等，按实际脚本逐步收紧）
- 登录限流、强密码；建议 2FA
- 上传白名单（扩展名/MIME）、杀毒或至少禁可执行文件
- 管理端 CSRF 防护、权限校验
- 联系表单验证码/限流（若有）

### 有流量后
- CDN + WAF
- 备份与监控告警
- 依赖漏洞定期更新

## 9. 仓库与工程组织建议

可选两种：

**A. Monorepo（推荐中长期）**
```
/
  apps/web          # 现有官网前台
  apps/admin        # 管理后台
  packages/shared   # 类型、内容 schema
  docs/             # 本指南与可编辑清单
```

**B. 双仓库**
- `official-web`：前台
- `official-cms`：Strapi/API + Admin

现阶段可继续单仓只做 `web`；阶段 2 再拆 `admin` 或接入 Strapi。

## 10. 里程碑与验收

| 里程碑 | 验收标准 |
|--------|----------|
| M1 前台定型 | 主页面视觉与动效通过评审；可编辑清单齐全 |
| M2 内容可配 | 改 CMS/API 数据后，前台对应区块变化 |
| M3 后台可用 | 运营能独立改首页文案与图片并发布 |
| M4 生产上线 | HTTPS、备份、基础安全、域名与监控就绪 |

---

## 11. 当前项目立刻怎么做

1. **继续做前台页面**，内容可写死。
2. 每完成一个区块，在 `docs/可编辑内容清单.md` 补一行字段（类型、建议尺寸）。
3. 组件内逐步把写死文案收拢到「区块配置对象」（仍可先本地 JSON），为接 API 打底。
4. 主页面稳定后，再选型 **Strapi/Directus** 或自建 API，开阶段 2。
5. **不要**现在并行做大而全后台。

## 12. 决策备忘

| 问题 | 建议结论 |
|------|----------|
| 框架要不要为后台换成 Next？ | 不必须；展示站 Vite React 足够，SEO 强硬需求再评估 |
| 一页一后台还是全部页面后再做？ | **主流程页面定型后再做后台**；最多先记字段清单 |
| 安全现在做吗？ | 开发期基本规范即可；**正式上线前集中补** |
| 图片继续放 public？ | 演示可以；接后台后改为对象存储 URL |
